# Spec: Close the six HIGH audit findings (H1–H6) without regressing the storefront

Version: 1

## Goal
Close the six HIGH findings H1–H6 with the smallest coherent change: approval and stock become authoritative on the write side, TND uses one declared unit end-to-end, checkout warns and reconfirms price changes, and `projection:replay` makes MIG-002 enforceable. Existing HTTP contracts, atomic stock behavior and order snapshots must not regress.

## Corrected prompt
Use the same `/spec` command that belongs to `.agent` in Qoder, then fix the high-severity problems.

## Open questions

- [BLOCKING] **H4 unit choice.** Whole dinars end-to-end (option 2) or millimes end-to-end (option 1)? Default if unanswered: whole dinars, because every existing value and seed is a whole dinar, the storefront fallback and `formatDT` already assume whole dinars, and it needs no data migration. Consequences to accept: TND is declared with scale 0 for this business, sub-dinar prices (e.g. 12.5 DT) are rejected, and `_minor`/`minor units` labels must be documented as "minor unit = dinar under the declared scale". If the business needs millimes, choose option 1 and accept a 1000× migration sequenced after the Catalog write model and executed through `projection:replay`, never by rewriting `*_view` rows in a migration.
- [BLOCKING] **H1/H6 topology.** Full Catalog write model for content + approval + publication (default), or an approval-only write model with `storefront_product_view` reclassified as a hybrid table and the docs claim corrected? Default: full write model. The approval-only option is much smaller but cannot honestly make `storefront_product_view` replayable, so R38 and R41 must then be rewritten to say "approval columns only; content is not replayable".
- [BLOCKING] **H2 auto-approval.** Keep the Super Admin edit auto-approval and make it auditable (default), or remove it and require an explicit `DecideCatalogSubmission` after every reviewer edit? Default: keep + audit, because the existing functional test asserts the behaviour and the audit's complaint is that it is silent and mislabelled, not that it is unauthorized. Removing it is a product decision and changes the approval workflow's UX.
- [BLOCKING] **Cutover and production data.** Is a short maintenance window acceptable, and is there production data outside dev/test? Default: assume production data may exist and require a short maintenance window; the backfill takes a table lock, runs dry-run then `--apply`, reconciles, then switches reads. If zero downtime is required, add dual-write and a feature flag to WP1/WP3.
- [BLOCKING] **Inventory `stockQuantity` meaning.** Does the admin field mean available quantity (default) or physical on-hand quantity? Default: available. If on-hand, an admin setting 5 while 2 are reserved leaves 3 sellable, which is a visible behaviour change and must be confirmed.
- [minor] **H5 confirmation shape.** Signed quote token (default) or client-supplied expected line prices/total? Default: token, because it cannot be tampered with and carries line-level detail. If no new signing/state is wanted, use expected lines and accept that a client can only weaken its own warning, never the charged amount.
- [minor] **MIG-002 grandfathering.** Do the two pre-existing data-writing migrations (`Version20261017000002`, `Version20261018000000`) count as MIG-002 violations? Default: grandfather both with reasons in the enforcement test and enforce only new migrations. Alternative: move the fixture seed and the taxonomy update to explicit commands, which changes first-boot behaviour and rewrites history.
- [minor] **Legacy backfill command.** Retire `app:catalog:backfill-approval` (default) and replace it with the write-model backfill + replay, or keep it as an operator command that writes the view? Default: retire; a command that writes a projection outside replay contradicts the new rule.
- [minor] **Search index after replay.** Should `projection:replay` reindex Meilisearch? Default: no; the existing `app:storefront:index-search` command remains the separate step, documented in the runbook.
- [minor] **Proxy orders.** Are staff-created proxy orders exempt from the customer price-change confirmation? Default: exempt, because staff see the current quote and are placing the order deliberately; the customer path is never exempt.
- [minor] **Approval audit action for an edit-approval.** Reuse `CATALOG_SUBMISSION_APPROVED` with a reason such as "approved by reviewer modification" (default), or add a distinct `CATALOG_PRODUCT_APPROVED_BY_EDIT` action. Default: reuse, to keep the audit vocabulary small.
- [minor] **Category table split.** Keep the name `storefront_category` for the projection and add a new `catalog_categories` write table (default), or rename the existing table and add a compatibility view. Default: keep the read name, because every query and API already uses it.
- [minor] **Admin read consistency.** Must every admin read be strongly consistent after a command (default), or is a short projection lag acceptable if the UI polls? Default: strong for admin, eventual for public.
- [minor] **Fulfilment stock transition.** Should a paid/shipped order convert `reserved` into an `on_hand` decrement? Default: no new fulfilment stock transition in this scope; the reservation stays committed, which preserves today's available-stock semantics. If fulfilment must decrement `on_hand`, a later event/subscriber owns it.

## Out of scope

- Medium/low findings from the audit, including RC4 lost-update handling for concurrent admin content edits, payment-failure compensation, delete-user PII/orphan cleanup, review-verification policy, `parent_slug` legacy cleanup and slug immutability enforcement.
- Event sourcing, an event store, aggregate rehydration from events, or a new bounded context/bus.
- Meilisearch projection replay/reindex beyond the existing search command.
- Multi-currency support, FX, tax, invoicing and rounding policy beyond the declared TND scale.
- A UI redesign; only the settings, cart and checkout changes required by H4/H5.
- Rewriting historical order data under the whole-dinar option.
- Payment gateway/provider changes and refund logic.
- Performance tuning unrelated to the new balance/replay queries (N+1, extra indexes) unless a HIGH fix cannot be correct without it.
- Any change to the public storefront payload that would expose approval metadata.
