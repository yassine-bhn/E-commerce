# Spec: Fix the six HIGH-severity audit findings (H1–H6)

Version: 1

## Goal
Resolve the six confirmed HIGH findings: catalog approval and inventory stock become authoritative on the write side and replayable, TND uses one unit convention end to end, checkout warns and reconfirms when a price changed, and `projection:replay` exists and is enforceable. Existing correct behaviour and API contracts must not regress beyond the additions listed here.

## Corrected prompt
Run the same `/spec` command that belongs to `.agent` in Qoder, then fix the high-severity problems.

## Assumptions
| # | Assumption | Risk if wrong (low / med / high) |
|---|------------|----------------------------------|
| 1 | H4 is fixed by the whole-dinar convention (TND has 0 fractional digits for this business), not by converting every amount to millimes. Product, cart, order and shipping data stay numerically unchanged. | high |
| 2 | H1 is fixed with an approval-only write model plus a projection. Product and category content stay in their current tables; a full catalog content write model is not required. | med |
| 3 | A super-admin content save must not approve a record. Approval is a separate, explicit action; the existing test that asserts otherwise encodes the bug, not the intended behaviour. | med |

| 6 | Existing `storefront_shipping_policy` values are already whole dinars. Values previously saved through the millime-converting UI are re-entered by an operator rather than guessed by a migration. | med |

## Open questions
- [BLOCKING] Is TND 0-decimal whole dinars for this business, or must all amounts be migrated to millimes? Default if unanswered: whole dinars end to end (R21–R22), no ×1000 data migration, seed `15` = 15 DT and `1000` = 1000 DT. R21–R26 already apply this default so workers are not left to choose.
- [minor] Must the full content of `storefront_product_view` become replayable, or is approval plus stock enough? Default if unanswered: approval and stock only; the docs explicitly scope the replay claim (R37) and a full content write model is out of scope.
- [minor] Should a super-admin save offer a single "save and approve" action? Default if unanswered: no; content save preserves status and approval uses the explicit decision command.
- [minor] What should happen to shipping values already saved through the old millime UI (e.g. 15000)? Default if unanswered: no heuristic rewrite; document that operators must re-enter the fee and threshold after deployment.
- [minor] Is HTTP 409 the right status for a price change? Default if unanswered: 409 Conflict with `error: "price-changed"`.
- [minor] Should the price-change warning appear on the cart page as well as at checkout? Default if unanswered: expose `priceChanged` on cart lines and block at checkout, so both surfaces can show it.
- [minor] Should `published` also move into the approval write model? Default if unanswered: no; it stays in `storefront_product_view` and is outside the approval write model.
- [minor] Should `catalog_submission` use a surrogate UUID primary key with a unique `(kind, slug)` pair? Default if unanswered: yes.

## Out of scope
- Medium and low audit findings, including payment-failure compensation, delete-user PII/orphan gaps, review verification policy, `parent_slug` legacy cleanup and slug immutability enforcement.
- A full catalog product/category content write model, event sourcing, an event store, or replay of every `storefront_product_view` content column.
- BRS race conditions RC4 (lost update between admins), RC5 (category cycles), RC6 (unpublish during checkout), RC7 (payment retry idempotency) and RC8–RC11, except where a requirement above explicitly touches them.
- Multi-currency support, tax calculation, promotion or pricing redesign.
- Migrating historical product, cart, order or shipping amounts to millimes.
- A redesign of the approval UI beyond making approval an explicit action and correcting its audit label.
- Meilisearch indexing changes that are not required to keep replay coherent.
- New Composer/NPM dependencies, CI/CD changes, deployment changes.
- Frontend visual redesign beyond the shipping unit fix and the price-change warning.
