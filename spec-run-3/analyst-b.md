# Spec: Admin dashboard CRUD endpoints for categories, users and banner images

Version: 1

## Goal
A separate admin frontend can drive the whole dashboard through JSON HTTP: it can create and organize categories (root + sub, hide, delete), administer users (list, change role, delete, see that user's orders), and maintain a homepage banner whose image count follows exactly what the admin uploaded — with no HTML, forms or UI work in this repository.

## Corrected prompt
This is the back end of an e-commerce site. In the admin dashboard, the admin must be able to manage:
- products — already implemented, nothing to do;
- categories — add a new category, add a sub-category under an existing category, delete a category, hide a category;
- users — delete a user, change a user's role between `ROLE_USER` and `ROLE_SUPER_ADMIN`, and see a user's orders;
- banner images — change the banner images; the banner must contain a dynamic number of images, driven by the images the admin uploads in the dashboard.

The frontend application is a separate project: I only need the back-end endpoints prepared for it. Implement the admin dashboard management CRUD.

## Assumptions

| # | Assumption | Risk if wrong (low / med / high) |
|---|------------|----------------------------------|
| A1 | "Hide a category" means a persisted visibility flag on the category record — the column does not exist today, so a schema change is expected — not soft-delete and not a multi-state enum. | med |
| A2 | "Manage"/"CRUD" (turn 2, line 2) means the same validation and conflict semantics the existing admin catalog endpoints already use (422 for invalid input, 409 for clashes, 404 for unknown rows), so these are required even though the prompt lists only add/delete/hide. | low |
| A3 | The admin SPA's working sequence is list → select → edit, so every write area needs a matching admin read: category tree (R11), banner list (R18), user list/detail (R30/R31). The prompt never names these reads, but "manage" is impossible without them. | med |
| A4 | The project harness rules bind this work: commands + handlers on `command.bus`, DBAL-only authorized finders, migrations reviewed and reversible, TDD, and the Definition of Done. New code therefore does not copy the raw-SQL-in-controller style of `AdminProductController`/`AdminCategoryController`. | med |
| A5 | The project's own business rules (BRG RG1.2 acyclic hierarchy, RG1.3 unique sibling names, RG1.5 non-empty category protection, RG3.4/3.5/3.6) still apply to the new endpoints, since the existing delete guard and `CategoryHierarchyValidator` already enforce them. | low |
| A6 | Hiding is a shopper-facing concern only: it removes the category from the storefront navigation, not from the admin list or from existing product assignments. | med |
| A7 | "The banner" is a single homepage carousel/hero concept whose slides are the uploaded images, in a meaningful order; the prompt says "a dynamic number of images", not "a dynamic number of banners". | med |
| A8 | Banner records store references to files already uploaded through the existing dashboard upload endpoint; no new binary-storage or image-processing path is introduced. | low |
| A9 | Admins need an active/inactive (publish) flag so a half-edited banner is not shown to shoppers. | low |
| A10 | Banner data belongs to an existing context (Catalog) as a new table rather than a new bounded context; adding a 9th context would be a boundary decision needing an ADR. | med |
| A11 | Changing a role grants dashboard access, so role editing is super-admin-only; the prompt only names `ROLE_USER` and `ROLE_SUPER_ADMIN` even though `ROLE_ADMIN` exists in the role hierarchy. | med |
| A12 | Invariants already enforced for ban/delete (audit trail RG3.5, last-super-admin preservation RG3.6) extend to role changes. | med |
| A13 | The admin SPA authenticates with the same session/cookie flow as the storefront, and its origin must be added to `STOREFRONT_CORS_ORIGIN` (today only `http://localhost:3000`). | med |
| A14 | The admin user list/detail must not expose password hashes or reset tokens; only fields the dashboard needs are returned. | low |
| A15 | "Delete a user" keeps the current delete-or-anonymize behaviour (RG3.4); no new hard-delete-only path is introduced for users with orders. | low |
| A16 | Definition of Done applies to the delivered endpoints (tests for each route, static analysis, deptrac), because this repo gates completion on it. | low |
| A17 | The shopper-facing frontend also consumes the banner, so at least one public banner read is in scope even though turn 2 says "endpoints for the frontend" — the banner is meaningless if nothing can read it. | med |
| A18 | A sub-category created from the dashboard is stored the same way the storefront already renders sub-levels today (the parent's nested `subcategories` JSON, validated by `SubcategoryTree`, which the product endpoint matches against) rather than as a separate category row with `parent_slug`; the repo currently supports both representations. | high |

## Open questions

- [BLOCKING] When the admin "adds a sub category", should it be a node in the parent's `subcategories` JSON tree (what `/storefront/reference` renders and what `AdminProductController::checkTaxonomy()` validates products against today) or a real `storefront_category` row with `parent_slug` (what `CategoryHierarchyValidator` cycle detection and the delete guard traverse)? The two representations are inconsistent today: a product can only be assigned to a top-level row plus a JSON label. Default if unanswered: JSON tree for sub-levels, `parent_slug` kept for existing rows (A18).
- [BLOCKING] Is the public banner read (R20) in scope, or does the separate admin app fetch banners and hand the list to the storefront itself? Turn 2 ("endpoints for the frontend only") is ambiguous about which frontend. Default if unanswered: ship the public banner read (A17).
- [BLOCKING] Should the role editor also allow `ROLE_ADMIN`? The dashboard firewall rule requires `ROLE_ADMIN`, and `ROLE_SUPER_ADMIN` inherits it, but with only the two named values there is no way to create a normal operator/staff account (BRG section 五.3 describes one). Default if unanswered: accept exactly `ROLE_USER` and `ROLE_SUPER_ADMIN` as stated (R24/R25) and leave `ROLE_ADMIN` unassignable.
- [minor] Does hiding a category also hide its products from the storefront product list, or only remove the navigation entry? Default: navigation only; products stay reachable (R13).
- [minor] Should hiding cascade to descendants/sub-levels in the storefront read, or must each be hidden individually? Default: cascade (R12).
- [minor] Maximum images per banner, and minimum (1 or 0)? Default: 1..12, `422` above the cap, `422` for an empty list.
- [minor] Does each banner image need alt text, a caption and a target link, or is a bare path enough? Default: bare path plus optional link/alt stored but not required.
- [minor] Is a per-image remove/append endpoint needed in addition to the replace-all endpoint (R16), or is replace-all enough for the SPA? Default: replace-all only.
- [minor] Should the uploaded file be deleted when a banner image is removed, or is orphan-file cleanup a separate job? Default: files are kept (R19).
- [minor] Page size, sort and filters for `GET /api/v1/admin/customers` (role, status, search, order count)? Default: `page`/`limit` (50 max), `q` over name/email/phone, `role` filter, newest first.
- [minor] Is the existing delete-or-anonymize behaviour for users acceptable as the dashboard's "delete", and does it need an explicit `confirm` field? Default: keep current behaviour (A15), no extra confirm field.
- [minor] Which role may perform each new action — `ROLE_ADMIN` for catalog/banner content and `ROLE_SUPER_ADMIN` for user/role/deletion actions (matching today's split where upload and product write are super-admin only)? Default: as written in R27 and R35.
- [minor] Does the category editor also expose `sort_order` and `quote_eligible` (both already stored), or stay to label/sub/hide? Default: expose both as optional fields; omitting them keeps current values.
- [minor] Should the endpoint contract be handed to the frontend team as a written document/OpenAPI file, or is code plus tests enough? Default: no new doc file.

## Out of scope

- Product CRUD, product image gallery work, brand and promo-code administration, order status transitions and proxy-order creation — all already implemented and only required not to regress (R40).
- Any admin UI, page, template or JS in this repository (`assets/`, `templates/` stay untouched) — turn 2 puts the UI in the separate app.
- New authentication, SSO, 2FA, granular per-screen permissions, or an admin account creation/invitation endpoint (creating admins is a different prompt than editing roles).
- User self-service profile editing, password reset, ban/unban (already implemented) — only delete, role change, list, detail and order history are requested.
- Deleting the physical image file, thumbnails, responsive crops, `srcset`, resizing, CDN/Meilisearch re-indexing, or orphan-file garbage collection.
- Banner scheduling, A/B rotation, targeting per governorate/customer, videos, or per-slide link tracking/analytics.
- Category merge/move/re-parent tooling, bulk import/export (CSV), translation/i18n of category labels, SEO metadata.
- Search-engine (Meilisearch) visibility semantics for hidden categories beyond the SQL read models.
- Stock/inventory, shipping zones, checkout saga, payment ledger changes.
- Reporting or dashboard widgets beyond "see the orders of a user" (no revenue charts, no order list filters for admins at large).
- New bounded context for content/marketing, and any change to `docs/adr/**` beyond what the implementers must record themselves.
- Rate limiting policy changes, audit-log viewer endpoints, and soft-delete/restore of users or categories.
