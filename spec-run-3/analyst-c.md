# Spec: Admin dashboard management endpoints — categories, users, banner

Version: 1

## Goal

A separate frontend app can drive an admin dashboard against this backend only: every action the
prompt lists (create / sub-create / delete / hide a category; delete a user, change a user's role,
read a user's orders; manage the set of images shown in the site banner) is reachable through a
documented, authenticated, JSON HTTP endpoint with defined success, validation, conflict and
authorization answers — and every case where the prompt collides with what actually exists in this
repo has been decided rather than discovered later by the frontend team.

## Corrected prompt

Backend only. In this repository the admin dashboard needs HTTP endpoints for:

- **Products** — already implemented, out of scope.
- **Categories** — create a top-level category; create a child of an existing category; delete a
  category; hide a category.
- **Users** — delete a user; change a user's role between `ROLE_USER` and `ROLE_SUPER_ADMIN`;
  read the orders belonging to a user.
- **Banner** — change the banner images; the banner shows a variable number of images taken from
  the images the admin uploads in the dashboard.

The consuming frontend is a different application; nothing here is UI work, only the endpoints it
calls, and they should be a management CRUD.

Two notes kept deliberately, because they change what "done" means: the last clause of the first
turn arrived truncated (`… related to the images upload`) and was restored by the orchestrator from
an earlier rendering of the same sentence, so the banner wording is *reconstructed, not verbatim*;
and "hide a category" names a capability for which this repo has no field, no read filter and no
test — see Q4/Q5.

## Open questions

- [BLOCKING] **Q1 — Which sub-category mechanism?** "Add a sub category" maps to either a `storefront_category` row with `parent_slug` (hierarchy exists in DB, but *nothing reads it*: `StorefrontReferenceRepository::categories()` selects only `slug, label, subcategories`, and no code ever writes `parent_slug`) or a node in the parent's `subcategories` JSON tree (`SubcategoryTree`, depth ≤ 4, label ≤ 128). Choosing wrong means re-doing the endpoint, its validation, its deletion guard (`ensureCanDeleteCategory` counts `parent_slug` children, not JSON children) and possibly a migration. Default if unanswered: JSON tree, because the uncommitted WIP test `tests/Functional/AdminCatalogTest.php:300-351` already pins exactly that payload shape; if the parent-row reading is meant instead, the public reference read must change too, which breaks the existing frontend contract.
- [BLOCKING] **Q2 — Delete semantics for a non-empty category:** the current code refuses (`CategoryNotEmptyException`, `422`). Keep refuse, or add explicit cascade/reparent/`force=true`? Also: does "has products" count products by `category_slug` only, or also products hanging on its sub-levels (today: only the direct `category_slug` match, so a category whose sub-tree holds products deletes cleanly and orphans them)? Default: refuse, direct products only.
- [BLOCKING] **Q3 — Should deleting a category be allowed at all once it ever had orders?** Order lines reference `product_slug`, not category, so category deletion is history-safe today; confirm no audit requirement ties orders to taxonomy. Default: allow once empty.
- [BLOCKING] **Q4 — What does "hide a category" hide, mechanically?** There is no `hidden`/`visible`/`enabled` column on `storefront_category` — grep over `src/` and `migrations/` for those words returns **zero hits** — so hiding requires a migration plus a filter in a *public* read path (`StorefrontReferenceRepository`, `StorefrontProductRepository`, and the Meilisearch index built by `IndexStorefrontSearchCommand`). Does hiding cascade to descendants? Default: new boolean column, hide subtree, admin list still shows it.
- [BLOCKING] **Q5 — Do a hidden category's products disappear from storefront product lists and search?** Nothing in the prompt says so; if they stay reachable, the storefront nav hides the entry but the product remains directly linkable and searchable. Default: products remain visible; only nav hides the category.
- [minor] **Q6 — Is editing/renaming a category in scope?** Not in turn 1's list, but the WIP test already asserts `PUT /api/v1/admin/catalog/categories/{slug}` including a "removing a subcategory still pinned by a product is refused" case. Default: keep the PUT because the WIP test demands it; treat as an extra beyond the prompt.
- [minor] **Q7 — Slug immutability:** `slug` is the PK of `storefront_category` and is referenced by `storefront_product_view.category_slug` and by `parent_slug`. Can it be renamed (cascading rename, as `AdminBrandController::rename` does) or is it frozen after creation? Default: frozen; renaming requires a separate decision.
- [BLOCKING] **Q8 — `ROLE_ADMIN` is missing from the prompt's enum.** The role hierarchy defines three tiers and `/api/v1/admin` requires `ROLE_ADMIN`; with only `ROLE_USER` ↔ `ROLE_SUPER_ADMIN` the dashboard cannot create a regular admin, cannot demote an existing `ROLE_ADMIN` to a legal value, and any `ROLE_ADMIN` row is unaddressable. Is that intended (2 roles only) or is `ROLE_ADMIN` the third option? Default: accept all three roles and keep `ROLE_ADMIN` non-settable via the dashboard only if the user says so.
- [BLOCKING] **Q9 — Self-service escalation:** may a `ROLE_SUPER_ADMIN` grant `ROLE_SUPER_ADMIN` to their own account, and may they demote *themselves* or the *last remaining* super admin? Today only deletion is guarded (`DeleteCustomerWithAnonymizationHandler:28-35`) — role writing does not exist at all, so nothing prevents removing the last super admin through the new endpoint. Also note the guard counts `status != 'banned'`, so a "last super admin" edit interplay with bans must be defined. Default: super-admin grants are super-admin-only, self-role-change is forbidden outright, last-active-super-admin is immovable.
- [BLOCKING] **Q10 — Who may do user management?** Existing split: ban/unban is `ROLE_ADMIN`, delete is `ROLE_SUPER_ADMIN` (`AdminCustomerController:90`). Which actor applies to role edit, user list and user-orders read? Default: mirror it — admin reads, super admin writes roles and deletes.
- [BLOCKING] **Q11 — Banner cardinality:** minimum and maximum number of images, and is there a per-image active flag? "Dynamic number" only says "not fixed". Default: 1..10, no active flag (deletion is the removal mechanism).
- [BLOCKING] **Q12 — Banner ordering and replacement model:** is the list ordered by an admin-set `sort_order`, by upload date, or by id? Is the change performed as per-item CRUD (`POST`, `PATCH/{id}`, `DELETE/{id}`) or as a whole-set replacement (`PUT` the ordered list)? Turn 1's only banner verb is "change the banner images"; turn 2 says "crud" — they imply different endpoints. Default: per-item CRUD plus a sort field, with an explicit re-order call.
- [minor] **Q13 — Does deleting a banner image delete the file?** No endpoint in this repo deletes files today (product delete drops only the DB row, leaving the image under `public/uploads/products/`). Default: DB row only, files accumulate.
- [minor] **Q14 — Public banner read path:** is the banner served by a new `GET /api/v1/storefront/banner` or folded into the existing `GET /api/v1/storefront/reference`? The latter changes a response the live frontend already parses. Default: new dedicated endpoint.
- [minor] **Q15 — Banner content beyond images:** captions, links, CTA, alt text, mobile/desktop variants, per-page or date-scheduled banners? None appear in the prompt. Default: image path + sort order + id only.
- [BLOCKING] **Q16 — Write path: CQRS or the existing raw-SQL admin precedent?** R40 needs one answer, and the repo contradicts itself: `AdminProductController`/`AdminBrandController`/`AdminCategoryController` write straight into read/reference tables with no command, handler, aggregate or outbox, while AGENTS.md 2/4/5 and the "NEVER dispatch domain events outside the outbox" NEVER say otherwise. Whatever is chosen also decides whether the category and banner work is cheap (controller+DBAL, 4 files) or expensive (commands, handlers, aggregates, projections, outbox, migration — ~15 files each). Default: follow the admin precedent and record the exception in an ADR; do not silently mix.
- [BLOCKING] **Q17 — Does "delete a user" mean the existing anonymize-or-hard-delete endpoint or a new plain delete?** The existing one already implements RG3.4, is super-admin-only, and does *not* implement BRD RC11 (block delete while an order is in flight) nor scrub order PII. Re-specifying delete from scratch would replace working behavior. Default: extend the existing handler for R17/R18/R19, keep its route.
- [minor] **Q18 — Does deleting/anonymous-ing a user reach orphaned rows without FKs?** `storefront_cart`, `storefront_wishlist_item`, `customer_password_reset_token` and quote records have `customer_id` but no FK to `customer_profile`, so nothing enforces cleanup today. Default: enumerate and delete them (R18).
- [minor] **Q19 — User-orders payload shape:** reuse the storefront's already-shaped customer order DTO (`CustomerOrderFinder`: order number as `id`, `placed_at` truncated to date, snake→camel keys, per-order N+1 line fetch) or return admin-shaped raw rows? Reusing inherits an N+1 (PRF-001) and a truncated date. Default: new admin read, single query with a `WHERE order_id IN (...)` line fetch.
- [minor] **Q20 — Pagination and filters on the user list and user-orders read** (search by name/email, filter by role/status, date range). Not asked for. Default: page/size only, no filters.
- [minor] **Q21 — Session and CORS:** authentication is session-cookie based (`LoginAuthenticator`, no token), and CORS origins come from `STOREFRONT_CORS_ORIGIN`; "the frontend app is a separated one" therefore needs credentialed cross-origin cookies. Is the admin app already on an allowed origin, and is `SameSite`/`credentials` configuration in scope? Default: out of scope, flagged to the frontend team; no config change.
- [minor] **Q22 — Concurrency (BRD RC4) on category/banner edits:** version check or accept lost updates? The admin endpoints have no `version` column on these tables (`version` exists on `ordering_orders` only). Default: accept; RC4 is recorded as unimplemented for these surfaces.
- [minor] **Q23 — Reliability of the restored truncated clause (A9).** The banner sentence was recovered from "an earlier identical rendering" after the client's copy was cut at `images upload`; nothing verifies it was the full clause. Confirm the banner bullet ends there. Default: proceed as restored; add nothing about captions/links.
- [minor] **Q24 — Are `quote_eligible` and `sort_order` on the category admin surface editable?** Both exist as columns, the WIP test sends `quoteEligible` but never `sortOrder`. Default: `quoteEligible` settable, `sort_order` auto-assigned.
- [minor] **Q25 — Seed/fixture impact:** `Version20261018000000.php` truncates and re-seeds `storefront_category`; any hidden flag added later must have a default that keeps the seeded taxonomy visible. Default: `hidden = false` default, backfilled.

## Out of scope

- Any admin UI, template, JS, component or asset in this repo — the frontend is a separate app (turn 2).
- Product management endpoints: create/update/delete already exist and the prompt marks them done.
- Brand, promo-code, shipping-policy, governorate, FAQ and platform-parameter management; they exist or were not named.
- Creating, registering, inviting, or un-banning users; banning already exists and is not in the prompt; password resets; impersonation.
- Fine-grained permissions, per-context admin scopes, teams, or anything beyond the role values named in the prompt.
- Media library, image cropping/resizing/thumbnails/optimization, CDN, storage backend change, orphan-file garbage collection.
- Banner captions, CTA links, per-page/scheduled/targeted banners, A/B variants, click/impression analytics.
- Order management: listing, status transitions, proxy orders and audit already exist in `AdminOrderController`; only "see the orders of a user" is in scope.
- Cart, checkout, stock, payment, Meilisearch index rebuild policy.
- Realtime/async work: no event.bus subscriber, saga or outbox flow is introduced by this spec unless R40's ADR decides the CQRS path.
- Rate limiting, 2FA, IP allowlists, GDPR export, data-retention jobs.
- Deployment, FrankenPHP/Caddy, CORS origin values, CI/CD.
