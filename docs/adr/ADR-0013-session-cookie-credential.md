# ADR-0013 — Session credential is an HttpOnly cookie

Status: accepted. Relies on: SEC-005, ADR-0010, ADR-0011, spec R1-R13 (`spec-run-11/spec.md` v2). CSRF follow-up delivered in F-csrf-origin-guard.

## Context

The storefront (`Zidane_front_web/`, Next.js, `STOREFRONT_DOMAIN`) and the API (`APP_DOMAIN`) are separate hosts. Authentication is session based: `POST /api/v1/auth/login` is handled by the custom JSON `LoginAuthenticator` (`src/Identity/Infrastructure/Security/LoginAuthenticator.php`), which returns identity only — `{id, email, roles}` — while Symfony persists the session server-side and the browser keeps the session id. `GET /api/v1/auth/me` (`src/Identity/Infrastructure/Http/AuthController.php`) is the only probe of that session, and `POST /api/v1/auth/logout` is handled by the firewall.

The storefront mirrors UI state in `localStorage` under `ziden-store-v1` (`Zidane_front_web/src/lib/store.tsx`). Earlier builds of the storefront stored the signed-in user in that payload, which is JavaScript-readable and therefore a copyable credential-shaped value (XSS exfiltration, another visitor's stale identity on a shared browser). The requirement is that whatever keeps a customer signed in is unreadable from JavaScript, and that no credential reaches Web Storage.

## Decision

Use the framework session cookie as the one and only session credential, and keep the storefront's persisted state credential-free.

- **Transport.** The session id travels only in the `Set-Cookie` header written by `AbstractSessionListener` from `framework.session.cookie_*` (`vendor/symfony/http-kernel/EventListener/AbstractSessionListener.php`). No endpoint returns it: login returns `{id, email, roles}`, register returns `{id, email, roles, status}`, `/me` returns identity, and the Google callback is a `RedirectResponse` (`src/Identity/Infrastructure/Http/GoogleOAuthController.php`).
- **Attributes.** `config/packages/framework.yaml` sets `cookie_httponly: true`, `cookie_samesite: lax`, `cookie_secure: false`, `cookie_path: /`; `when@prod` sets `cookie_secure: true` and `cookie_samesite: none`. `HttpOnly` is environment-independent; `Secure`/`SameSite` follow the environment. The remember-me cookie mirrors the same policy (ADR-0011).
- **Why `SameSite=None` in production.** It is the value shipped today and the one ADR-0011 already assumed. Note what the repository actually proves: `deploy/Caddyfile` proxies two separate *hostnames*, and `.env.prod.example` shows `api.example.com` / `shop.example.com`, which are the **same registrable domain** — i.e. same-site, where `SameSite=Lax` would be sufficient and strictly stronger against CSRF. The real production hostnames are not recorded anywhere in the repo, so this ADR keeps the delivered value rather than flipping a live policy on an unverified guess; confirming the topology is a follow-up.
- **Attaching the credential.** `Zidane_front_web/src/lib/api/client.ts` sends `credentials: "include"` on every verb; no `Authorization` header exists in the codebase and no raw `fetch` bypasses the client.
- **Storefront state.** `ziden-store-v1` keeps only guest UI state: guest cart, guest wishlist and language. It is always written with `user`, `orders` and `addresses` empty, and a payload left by an older build is sanitised on load (`user`, `orders` and `addresses` deleted before the merge). `GET /api/v1/auth/me` is the only source of a signed-in user; a 401 clears the in-memory user, and a login/logout that happened while that probe was in flight wins over its result. `authReady` gates auth-dependent rendering.
- **Revocation.** Logout expires the session cookie, clears the remember-me cookie, and destroys the session server-side: replaying the pre-logout session id answers 401. See `SessionCookieTest::testLogoutExpiresTheSessionCookieAndRevokesTheSession`.
- **Cross-site posture.** CORS stays a **response** policy: `src/Shared/Infrastructure/Http/CorsSubscriber.php` answers preflight and sets the headers, and never rejects a request. The request-side control is a separate listener, `CrossSiteRequestGuardSubscriber` (`src/Shared/Infrastructure/Http/`), on `kernel.request` at priority 14 — after the router (32) and before the firewall (8), so a refused request is never authenticated and never given a session, and below `CorsSubscriber` (256). It judges the path the router matches, not the raw bytes on the wire: the path is decoded once with `rawurldecode()` — mirroring `UrlMatcher::doMatch()` — before the `/api/v1` prefix is checked, so a percent-encoded spelling of the prefix (`POST /api%2Fv1/storefront/orders`) is refused like the plain spelling; a second decode is deliberately absent, because it would diverge from routing in the other direction. It refuses state-changing `/api/v1` requests (POST, PUT, PATCH, DELETE) whose first present signal is untrusted, read in the order `Origin` → `Referer` origin → `Sec-Fetch-Site: cross-site`; trusted means the request's own origin or an entry of `STOREFRONT_CORS_ORIGIN`. `Origin` values and the allow-list have one shared interpreter: the `Origin` value object and `OriginAllowList` in `src/Shared/Domain/Http/` (pure PHP, no framework coupling), split and parsed once at construction and consumed by both the guard and `CorsSubscriber`, which keeps echoing the raw `Origin` header value so the browser comparison is unchanged. The request's own origin derives from the request's scheme and host — the `Host` header, or `X-Forwarded-Host` when the connection comes through a proxy the application trusts — so the trusted-proxies configuration, not the guard, decides which header defines "own origin". The refusal is `403 {"error": "Cross-site request refused."}`. A request carrying none of the three signals is not refused: non-browser clients and provider webhooks send none, and the whole existing test suite drives the API without them. `OPTIONS` preflight never reaches the guard, because `CorsSubscriber` answers it at 256 and `RequestEvent::setResponse()` stops propagation.

## Rejected alternatives

- **JWT or any token in `localStorage`/`sessionStorage`.** Rejected: it is readable by any script on the page, survives a tab close, and can be exfiltrated without the victim noticing. It would also add a second validation path outside the firewall, next to the session that already exists. This is the alternative the requirement explicitly forbids.
- **A `localStorage` mirror of the signed-in user kept in sync with `/me`.** Rejected: it is not a credential today, but it is a copyable identity that an XSS payload or the next developer turns into one, and it makes the UI claim a session the API may already have refused.
- **`__Host-` prefixed cookie name.** Rejected for this change: it hardens subdomain/Downgrade attacks but renames the cookie, which signs every live customer out on deploy. Tracked as a separate, deliberately scheduled decision.
- **Bearer token in the JSON login body plus a memory-only store.** Rejected: the credential would be lost on reload and re-issued on every refresh, and the session cookie would still exist for the firewall, so two credentials would coexist.
- **New CSRF tokens on every JSON endpoint in the same change.** Rejected here: it is a real hardening step for a `SameSite=None` deployment, but it is a separate decision with its own trade-offs (preflight, double-submit storage, mobile clients) and would widen this change beyond the credential move.

## Accepted trade-offs (non-properties)

- **No CSRF token; a browser-enforced origin check.** The guard adds no token: `config/packages/csrf.yaml` only declares stateless token ids (`submit` for forms, plus `authenticate` and `logout`) and no endpoint or firewall option validates one, and the cookie is still sent on `SameSite=None`. The control is browser-enforced only — `Origin` and `Sec-Fetch-Site` are client-controlled (as is `Referer`), so a non-browser client that omits them is not refused — and it is coupled to CORS: the guard trusts exactly the `STOREFRONT_CORS_ORIGIN` allow-list, so widening CORS widens the CSRF allow-list. The allow-listed origin is therefore a **write trust anchor**, not just a CORS reader: its entry does not merely permit reading responses — it is trusted to authorise state changes under a visitor's session, so a compromise of that origin (an open redirect, injected markup) now yields POST/PUT/PATCH/DELETE on the API, and its redirect and HTML hygiene is part of this control's trust base. A cross-site `POST` with `Content-Type: text/plain` is a simple request that needs no preflight, and CORS withholds the response only after the side effect has run; the guard is what refuses it, and only when the request announces a site.
- **Logout accepts `GET`.** `identity_logout` is routed for `POST` and `GET` and is `PUBLIC_ACCESS` (`config/packages/security.yaml`), so a cross-site `GET` can sign a visitor out (annoyance, not credential theft). Left as is to keep this change narrow; recorded as a follow-up.
- **The session cookie is a browser-session cookie.** No `cookie_lifetime` is set (`config/packages/framework.yaml`); persistence across a browser restart is the remember-me credential's job (ADR-0011), so a customer without "remember me" is signed out when the browser closes.
- **The persisted storefront payload is still JavaScript-readable.** It now holds only a guest cart, a guest wishlist and the language — no identity, no order, no address, no credential — so an injected script can read a guest's browsing choices but cannot copy a session or account data. Account data (`orders`, `addresses`) is intentionally not mirrored to storage; it is read from the API per session.
- **Cross-tab sign-out is eventual.** With no user mirror in storage, another tab learns about a sign-out on its next `/me` call rather than through a `storage` event.
- **One credential for storefront and admin.** The `main` firewall protects `/api/v1/admin` as well; the blast radius of a stolen session is role-wide until the session is destroyed.

## Consequences and follow-ups

- **Positive:** the session id is unreadable from JavaScript in every environment; no credential and no account data is written to Web Storage; the storefront can no longer show a signed-in UI on a session the API refused; logout destroys the session server-side; the policy is pinned by tests that fail when `HttpOnly` or the per-environment flags change.
- **Negative:** the guard is a browser-enforced origin check, not a CSRF token. A non-browser client that omits `Origin`, `Referer` and `Sec-Fetch-Site` is not refused, `SameSite=None` still attaches the cookie to a cross-site request, and nothing beyond the cookie itself binds the request to the session; the announced cross-site case is closed, CSRF in general is not.
- **If** defence against non-browser clients is required, then add a double-submit CSRF token on the cookie-authenticated JSON endpoints — the origin guard judges only signals a browser sends; the `SameSite=Lax` switch below covers the browser path.
- **If** the real production `APP_DOMAIN`/`STOREFRONT_DOMAIN` share a registrable domain (as `.env.prod.example` suggests), then switch `when@prod` to `cookie_samesite: lax` and update the expectation pinned in `tests/Integration/Identity/SessionCookiePolicyTest.php`; that removes most of the CSRF exposure above.
- **If** `identity_logout` must stop being cross-site triggerable, then drop `GET` from the route methods in `src/Identity/Infrastructure/Http/AuthController.php` and update the storefront (which already uses `POST`) before the next deploy.
- **When** the cookie name is next revised, consider `__Host-` (requires `Secure`, `Path=/`, no `Domain`) and schedule it with a forced re-login window.

## Proof (regression tests)

- `tests/Functional/SessionCookieTest.php` — login answers with an `HttpOnly` session cookie and no token field, the cookie alone authenticates `/me`, logout expires both credentials and revokes the session (the pre-logout id is replayed and refused), register returns identity only and starts no session.
- `tests/Integration/Identity/SessionCookiePolicyTest.php` — composed `session.storage.options` and the emitted cookie are `HttpOnly` everywhere, `Secure` + `SameSite=None` in production, `SameSite=Lax` and non-secure in `dev` and `test`.
- `tests/Functional/CsrfOriginGuardTest.php` — a valid login from a foreign `Origin` answers 403 with no session opened; the configured storefront origin and the request's own origin answer 200 with a session; a foreign `Referer` answers 403; `Sec-Fetch-Site: cross-site` answers 403 while `same-origin`, `same-site` and `none` do not; a request with no signal answers 200; `GET`/`HEAD` are never refused; `OPTIONS` preflight still answers 204 from a foreign origin; `POST /healthz` is answered by the router (405), never 403; order creation is 403 from a foreign origin and 201 from the storefront origin, with no order row and unchanged stock after the refusal; and percent-encoded spellings of the prefix (`POST /api%2Fv1/auth/login`, `POST /api/%76%31/auth/login`) answer 403 with no session opened, like the plain spelling. The pins are proven by mutation of the guard — the round-1 negative control; the decode-once rewrite is not re-mutation-tested, and its new branches are covered by the unit tests below — except the `OPTIONS` pin: `CorsSubscriber` answers preflight at priority 256 and `RequestEvent::setResponse()` stops propagation, so the guard never sees it and no mutation can fail that pin.
- `tests/Unit/Shared/Http/OriginTest.php`, `tests/Unit/Shared/Http/OriginAllowListTest.php` — the shared interpreter below the HTTP layer: `Origin` lowercases scheme and host, elides default ports (80/443) while keeping explicit non-default ones, accepts only `http`/`https`, and yields no origin for unparseable input; `OriginAllowList` splits `STOREFRONT_CORS_ORIGIN` once (comma-separated entries, surrounding whitespace trimmed) and answers both the match and the miss.
- `tests/Integration/Identity/RememberMeCookiePolicyTest.php`, `tests/Functional/RememberMeTest.php`, `tests/Functional/CorsTest.php`, `tests/Functional/GoogleOAuthTest.php` — unchanged and still green.
- `Zidane_front_web`: `npm run typecheck` and `npm run lint` (no test runner is wired in the storefront). The `credentials: "include"` rule is checked by inspection of `client.ts` — the only `fetch` in the storefront tree — not by an automated test.
