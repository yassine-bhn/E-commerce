## 一、参与者与权限矩阵

平台定义了四类业务参与者：
1. **匿名用户（访客）**：未登录的访问者。
2. **注册用户（客户）**：已完成注册并成功登录的终端顾客。
3. **管理员（运营人员）**：负责日常商品、目录、促销及用户履约管理的后台操作人员。
4. **超级管理员（系统掌舵人）**：拥有平台最高全局权限，独自负责管理员生命周期及全局平台规则配置。

## 二、核心业务概念

### 1. 分类（Category）
- 组织商品的层级结构，支持树状体系。
- **根分类（Root Category）**：层级最顶层的分类，无父级。
- **子分类（Sub-Category）**：隶属于特定父分类的下级分类。分类关系单向向下，严禁形成环形回路。

### 2. 商品（Product）
- 平台销售的实物或服务实体。
- **单类目归属原则**：每个商品在任何时刻**必须且只能归属于一个分类**（该分类可以是根分类，也可以是任意子分类）。商品不得悬空存在，也不得多重挂载。

### 3. 促销（Sale）
- 针对特定商品或特定分类实施的限时价格优惠机制。
- 核心商业属性包含：**有效起止时间窗口**、**折扣类型**（如固定折扣金额、百分比让利）、**折扣额度**、**生效状态**（草稿、已排期、进行中、已结束、已终止）。

### 4. 订单与支付（Order & Payment）
- **常规在线订单**：由已登录的注册用户通过购物车校验、提交后生成，支持在线支付通道并自主结算。
- **电话 / WhatsApp 沟通订单**：针对无法使用在线购物车结算的匿名用户，由商家线下沟通后受理并生成的特殊履约订单。
- **独立支付状态**：订单与支付记录解耦，支付包含独立生命周期与交易流水，用于应对网络延迟、重复提交及交易对账。

## 三、匿名用户购买业务流程（电话 / WhatsApp 专项说明）

由于匿名用户无权使用在线购物车及自助结算流水，平台提供**“人工通道（电话/WhatsApp）”**作为其商业闭环方案。

### 1. 业务流程与职责流转
1. **浏览商品与查阅联系方式**：匿名用户在前台商品详情页查阅商家官方服务电话或 WhatsApp 咨询按钮。
2. **离线意向沟通**：匿名用户发起通话或聊天，说明意向商品型号、数量与诉求。
3. **查验与报价**：管理员在后台管理系统中核验即时库存与生效价格，给出最终总价（含运费）。
4. **收集履约信息**：用户确认后，向管理员提供收件人姓名、联络手机号、详细配送地址。
5. **系统代客录单**：管理员在后台创建“电话/WhatsApp代客订单”，录入用户基础信息，系统即刻执行库存锁定（进入待支付状态）。
6. **付款凭单确认**：顾客通过线下银行转账/即时二维码支付并回传付款凭证（或确认货到付款 COD）。
7. **收款核销与履约发货**：管理员在后台系统核验款项后，手动点击“确认收款”，订单状态更新为“已支付”，转入仓库分拣发货。

### 2. 核心业务细节规范
1. **订单代录人**：统一由管理员或超级管理员在运营后台代录。录入时必须标明订单来源（如 `PHONE_OR_WHATSAPP`）。
2. **必需收集的履约信息**：
   - 顾客姓名、联络手机号（必须作为订单主联系人，以便派件追踪）。
   - 完整收货地址（省/市/区/详细街道门牌号）。
   - 目标商品的精确规格、购买件数。
   - 顾客期望的履约方式（转账预付或货到付款）。
3. **库存与价格锁定机制**：
   - 管理员录入代客订单时，系统即刻执行**预占库存（锁定）**，进入“待支付”阶段。
   - 预占库存享有业务保护期（默认超时自动释放）。
   - 订单成交价格严格以管理员在系统录入按下确认时刻的有效价格快照为准。
4. **收款方式与核销**：
   - 采用线下银行汇款、即时收款钱包（如 WhatsApp Pay/商户二维码）或货到付款（COD）。
   - 财务核款后，由管理员在后台点击“确认收款”，系统将支付记录更新为“已支付”，进入发货待配货状态。
5. **引导注册触点**：
   - 当匿名用户在商品页尝试添加购物车时，系统中断操作并弹出友善提示：“购物车与在线追踪功能仅对注册会员开放，请先[登录/注册]或通过[电话/WhatsApp]联系专属客服快捷下单”。

## 四、业务规则定义

### 1. 目录规则（Catalog Rules）
- **[RG1.1] 强制归属原则**：新建或编辑商品时，必须为其指定唯一的分类；脱离分类的商品禁止保存入库。
- **[RG1.2] 分类拓扑无环**：分类支持多层级，但必须保持单向树形结构。系统严禁将父分类移动为其自身子孙分类的下级，杜绝循环依赖。
- **[RG1.3] 同级名称唯一**：在同一个父分类之下，所有直接子分类的展示名称必须具有唯一性，不得同名混淆。
- **[RG1.4] 历史关联保护**：凡已产生过业务订单（含已取消、已支付历史）的商品，禁止执行物理删除；系统仅允许将其状态置为“已下架”或“隐藏”，以确保历史订单快照与核算审计完整。
- **[RG1.5] 非空分类保护**：分类内若尚存在有效商品，或其下挂载有子分类，该分类禁止直接删除。必须先清空或转移其下属商品和子分类后方可操作。

### 2. 促销规则（Promotion Rules）
- **[RG2.1] 运营管理专有权**：仅管理员和超级管理员具备查看促销配置、创建新活动、调整让利规则与提前终止活动的权限。
- **[RG2.2] 时间窗口约束**：任何促销仅在其设定的“起始时间 ≤ 当前系统时间 ≤ 截止时间”之内生效；未到期为预告，过期即刻失效。
- **[RG2.3] 价格合理性红线**：促销最终折后价必须严格遵循 `0 < 促销折后价 < 商品原售价` 的业务数学规则，禁止产生 0 元甚至负数价格。
- **[RG2.4] 最优让利仲裁**：当同一件商品同时命中多项生效中的促销政策时，系统默认选择**对顾客最有利（折后价格最低）**的一项计算结算总额，禁止隐式折上折叠加。
- **[RG2.5] 价格透明展示**：处于促销有效期的商品，用户界面必须同时呈现**划线原售价**与醒目的**促销让利价**，保障消费者知情权。

### 3. 用户与安全管理规则（User & Access Rules）
- **[RG3.1] 越权操作隔离**：普通管理员的权限受限，仅可对普通注册用户执行管理操作（封禁、解封、删除）；严禁操作其他管理员或超级管理员账号。
- **[RG3.2] 审慎封禁机制**：管理员执行用户封禁操作时，必须在系统界面填写合规的“封禁原因”；封禁属于可逆管控措施，查明事实后允许管理员撤销封禁并恢复账户权限。
- **[RG3.3] 被封禁状态限制**：账户处于“已封禁”状态的用户，禁止登录系统，禁止提交新订单，禁止参与购物车结算，且无权发起即时聊天咨询。
- **[RG3.4] 用户删除与订单匿名合规**：当删除已产生订单的用户时，严禁级联删除该用户的历史履约数据。系统必须对历史订单执行“脱敏匿名化归档”（抹除账户登录名、头像等个人信息，但必须完整保留财务金额、下单快照与物流明细），满足财务与法律审计要求。
- **[RG3.5] 全程审计追踪**：所有针对用户的“封禁”、“解封”、“删除”操作，系统必须自动向不可逆的审计日志中记入操作人身份、操作时间、目标对象及操作说明。
- **[RG3.6] 超级管理员底线保全**：全平台必须永久至少保留一个处于激活状态的超级管理员账号，系统拒绝任何会导致超级管理员数量归零的删除或停用申请。

### 4. 结算与访问准入规则（Access & Checkout Rules）
- **[RG4.1] 购物车权限准入**：匿名用户禁止使用购物车；仅限状态正常且未被封禁的已登录注册用户使用购物车添加与结算商品。

## 五、各参与者功能清单

### 1. 匿名用户（访客）
- **浏览选品**：浏览全部分类目录结构，查看分类下的商品陈列与促销标牌。
- **检索定位**：根据关键字、分类筛选查找商品及促销信息。
- **商品探查**：查阅商品图文详情、划线原价、现时折扣价与现货状态。
- **人工通道**：查看商家官方联络方式（电话号码一键拨打、WhatsApp 跳转对话），沟通意向直接下单。
- **身份转换**：根据提示前往注册新用户账号，或登录已存在账号。

### 2. 注册用户（登录客户）
- **享有访客全部基础权益**（浏览、搜索、查阅促销等）。
- **个人中心维护**：编辑维护个人昵称、头像、修改登录密码、维护多条常用收件地址（设置默认地址）。
- **购物车管理**：将商品加入购物车、修改选购件数、勾选结算项目、删除无意向商品。
- **自主在线结算**：基于购物车发起结算流程，锁定收件地址，提交在线订单，调起支付通道并完成支付。
- **订单履约查询**：查看属于个人的所有历史订单、实时履约流转状态（待支付、已支付、已发货等）及物流追踪。
- **客服沟通**：享有发起客服沟通的资格（权限预留）。

### 3. 管理员（运营主管）
- **类目与商品运营**：
  - 创建、编辑根分类和子分类（校验层级拓扑）。
  - 创建、编辑商品（标题、说明、原价、多图、单类目挂载）。
  - 商品状态维护：商品上线开售、下线停售（下架）、调整现有库存数量。
  - 删除空分类及未售卖过的草稿商品。
- **营销活动治理**：创建限时促销、配置优惠规则、修改活动期限、强制终止异常促销。
- **电话/WhatsApp 订单承接**：在运营后台代客新建订单、录入顾客地址、核实库存价格、确认到账核销。
- **客户生命周期管控**：查询普通客户列表、查看详情；执行合规封禁（录入原因）、解除封禁；对注销用户执行合规删除。
- **客服接待**：享有与客户交流的业务权限（权限预留）。

### 4. 超级管理员（最高决策人）
- **享有管理员的全部业务功能权限**。
- **管理员团队管理**：
  - 创建新的管理员账号并配置业务范围。
  - 临时停用管理员权限，或在人员变动时永久注销管理员账号。
- **平台配置中枢**：
  - 配置平台官方服务电话与 WhatsApp 联络号码。
  - 配置支付通道参数、自动取消超期未支付订单的时间阈值等全局参数。
- **审计日志审阅**：查阅涉及账户封禁、数据注销、订单异常调控等全量安全合规审计流水。

## 六、竞态条件业务处理表（Race Conditions）

| 编号 | 竞态场景 | 业务风险 | 期望的业务行为与解决标准 |
| :--- | :--- | :--- | :--- |
| **RC1** | **两人同时抢购最后一件现货商品** | 系统超卖，库存变成负数，导致其中一位顾客无法履约交付而引发客诉。 | **绝对禁止超卖与负库存**。系统采用原子化库存扣减准则。第一个提交成功的请求成功扣减并锁定该件库存；后到达的请求即刻被系统拦截并提示：“抱歉，该商品刚刚售罄”，订单提交失败。 |
| **RC2** | **在线用户下单与商家代客下单同时争夺最后一件库存** | 电话客户与在线客户同时被承诺有货，引发线下纠纷与商业信誉受损。 | **先锁先得，统一仲裁**。不论请求来自在线购物车结算还是管理员后台代客下单录入，必须通过同一中心库存核验。先到达并成功核减的一方获得配额；后触发的一方提示“库存不足，已被其他订单锁定”，商家需向电话顾客致歉或引导选购其他替代款。 |
| **RC3** | **用户结算时管理员正调整商品原价或修改促销** | 顾客按高价结算引发欺诈投诉，或按管理员误操作的超低价结算造成商家损失。 | **以下单确认时刻的快照为准**。若用户已进入“核对订单并点击提交”的确认时刻，系统锁定当时的单价并生成订单快照，后续管理员的改价仅对之后产生的新订单生效；若改价发生在用户点击提交之前，系统在结算界面给出“价格已发生变动”明确提醒，要求用户重新确认金额。 |
| **RC4** | **两位管理员同时在后台编辑保存同一商品或分类** | 后保存的人无意间覆写了前一人精心调整的内容（丢失更新 / Lost Update）。 | **后提交者阻断与重新加载**。采用版本校验。后点击保存的管理员将收到系统明确警告：“该数据已被其他管理员修改，请刷新并核对最新版本后再做编辑”，禁止静默无感覆盖。 |
| **RC5** | **两位管理员互移分类造成循环引用（如 A 放入 B，B 放入 A）** | 分类树形结构崩塌陷入死循环，前台分类导航无法展开瘫痪。 | **层级依赖前置阻断**。移动分类前执行拓扑路径有效性校验。第二个管理员提交时，系统检测到目标路径已经包含自身，强制中断操作并提示：“非法移动：目标分类隶属于当前层级下，无法移动产生循环依赖”。 |
| **RC6** | **管理员下架商品的同时，用户正在进行购物车结算** | 顾客结算付款成功，但仓库已停售该商品无法配发。 | **结算前拦截与阻断**。在用户点击最终“提交订单”的瞬间，系统校验商品“上架与可见状态”。若商品已被下架，系统阻断生成订单，并提示：“您选购的商品 [xxx] 已停售，已为您移出结算清单”。 |
| **RC7** | **用户重复狂点支付或网络抖动重试** | 同一笔订单在银行/三方渠道被重复扣款多次，引发账务差错及客诉。 | **严格幂等控制，单笔至多一次支付**。每笔订单的支付请求绑定唯一交易防重令牌。后续相同的重试请求在首笔交易处理完毕前直接排队拦截或返回处理中状态，绝对保证一个订单只生成一笔有效扣款流水。 |
| **RC8** | **三方支付成功结果回调与用户超时取消订单同时到达** | 系统既将订单作废关闭，又扣除了顾客钱款，出现“扣款却无订单”的资金悬挂。 | **以实际付款成功优先**。只要核实到合法的三方支付凭据真实成功扣款，系统强制撤销取消动作，将订单流转为“已支付”状态并正常发货履约；若业务上该订单确实无法恢复，系统必须记录挂账并自动发起原路无损退款任务。 |
| **RC9** | **订单已预留锁定库存，但用户长时间未完成付款** | 现货库存被无效长时间霸占，阻碍真正有购买意向的顾客下单，降低周转率。 | **倒计时超时自动释放**。系统对待支付订单设定固定倒计时保护窗口（如 30 分钟）。一旦超时仍未检测到有效支付，系统自动将订单流转至“已取消”，并即刻将锁定的库存足额归还至可售库存池中。 |
| **RC10** | **管理员封禁用户的同时，该用户正在进行支付中** | 违规受处罚人员依然成功消费或在平台上流转订单。 | **支付链路允许收尾，登录与后续履约即刻截断**。若资金扣减已进入银行底层通道无法撤回，系统允许该笔支付完成并生成订单，但该用户后续登录、浏览、发起聊天、再次结算将被即时阻断，订单后续履约由管理员在后台核实后人工介入处理。 |
| **RC11** | **管理员删除某用户账号时，该用户尚有进行中的在途订单** | 仓库找不到发货对象收件信息，或售后权益凭据丧失导致严重纠纷。 | **阻断删除，强制等待履约终态**。若该用户存在任何未完成的订单（待支付、待发货、待收货），系统坚决拦截管理员的删除指令，并提示：“该用户尚有正在履约中的订单，暂无法注销账号”。 |
| **RC12** | **两位管理员同时分别对同一用户下达“封禁”与“删除”指令** | 系统逻辑混乱，出现“已被物理抹除的用户又被写入封禁状态”等异常数据。 | **基于状态版本的互斥处理**。优先执行先到达的操作。若删除指令先完成，后到达的封禁指令将失败并提示“该用户已注销”；若封禁指令先完成，删除指令可基于被封禁的用户继续执行合规归档注销。 |
| **RC13** | **超级管理员停用某管理员时，该管理员正提交大批量目录调整** | 已被解雇或降权的管理员继续向系统写入敏感的商品和价格变动。 | **权限实时作废与事务拦截**。停用指令生效后，该管理员已持有的操作凭据即刻失效，其正在发送提交的目录修改请求将被系统直接拒绝，提示“权限已失效，操作未保存”，确保平台数据安全。 |

## 七、支付与订单的乐观并发机制（Optimistic Concurrency）

### 1. 核心业务规则
- **[RP1.1] 实体版本自增**：订单主记录与各笔支付业务记录均持有独立递增的“业务版本标识（Version）”。每当实体状态、金额、履约阶段发生任何实质性变更，该版本号必须自增 1。
- **[RP1.2] 基于基准版本提交**：任何参与者（包括用户端、管理后台、三方支付通道通知）提交变更请求时，必须明确提交其读取到的原始版本号；若当前系统内部版本已发生推移，系统坚决拒绝本次修改。
- **[RP1.3] 严禁非法跨级流转**：实体流转必须严格对照《订单与支付合法状态流转表》，禁止任何逆向操作或违背商业逻辑的越级跃迁（如从未支付直接跃迁至已发货）。
- **[RP1.4] 冲突零隐式重试**：当发生版本冲突被系统拒绝时，严禁系统在后台代客自动重试扣款操作，必须将最新真实状态拉取后呈现给用户或管理员由人工裁决，防止多扣资金。
- **[RP1.5] 金额锁定不可变**：一旦订单创建完毕进入待支付状态，应付总金额即刻被全面冻结，支付执行期间任何上游改价操作不得更改该订单已锁定的金额。
- **[RP1.6] 全量状态审计记录**：所有订单及支付状态的变更，无论成功还是因版本冲突被拒绝，必须记入全局业务审计轨迹。
- **[RP1.7] 周期性对账补偿**：平台每日定时拉取官方资金明细账单，对系统记录为“待支付”但实际在通道侧“已扣款”的掉单异常，执行对账补偿流转与预警。

### 2. 订单与支付合法状态流转对照表

| 现存原始状态 | 允许跃迁的目标状态 | 触发业务前提与合法场景 | 非法流转（一律坚决阻断） |
| :--- | :--- | :--- | :--- |
| **待支付** (Pending) | **已支付** (Paid) | 用户在线支付成功核销，或管理员查收线下转账后确认到账。 | 严禁跳至：已发货、已退款。 |
| | **已取消** (Cancelled) | 顾客主动取消未支付订单，或倒计时超时系统自动释放。 | 严禁跳至：已发货、已退款。 |
| | **支付失败** (Failed) | 银行账户余额不足、银行卡受限等原因导致通道扣款明确拒付。 | 严禁跳至：已发货、已退款。 |
| **已支付** (Paid) | **已发货** (Shipped) | 仓库已完成备货并已将包裹交接给物流快递，录入运单单号。 | 严禁跳至：待支付、已取消。 |
| | **已退款** (Refunded) | 订单缺货无法履约，或顾客在发货前申请退款并经审核批准。 | 严禁跳至：待支付、已取消、已发货。 |
| **支付失败** (Failed) | **待支付** (Pending) | 顾客决定更换支付手段或重新发起新一轮付款尝试。 | 严禁跳至：已发货、已退款。 |
| | **已取消** (Cancelled) | 顾客放弃重试支付，订单超时关闭。 | 严禁跳至：已发货、已退款。 |
| **已取消** (Cancelled) | *（终态，无后续流转）* | 订单生命周期终止，库存已返还，不可复活。 | 严禁跳至任何非终态。 |
| **已发货** (Shipped) | **已退款** (Refunded) | 顾客收到包裹后申请售后七天退货退款，退货验收入库完成。 | 严禁跳至：待支付、已取消。 |
| **已退款** (Refunded) | *（终态，无后续流转）* | 财务已原路返还款项，流程归档。 | 严禁跳至任何非终态。 |

### 3. 典型并发场景与期望业务裁决

- **场景 1：双标签页同时发起支付**：首个调起的交易锁定订单状态，第二个调起因版本号过期或正在支付中被拦截。
- **场景 2：支付成功回调与用户取消冲突**：实收资金优先原则。若三方已成功扣款，撤销取消操作，推进订单为“已支付”。
- **场景 3：银行重复回调**：基于交易流水号与版本号做幂等吸收，仅记录一次账单核销，不重复扣库存或流转状态。
- **场景 4：支付期间订单被修改**：待支付订单进入支付链路后锁定金额与明细，修改操作因版本过期被拒绝。
- **场景 5：支付成功但系统订单更新失败（掉单）**：资金流水独立留存，系统通过定期自动对账任务将订单状态补偿推进至“已支付”，通知履约发货。
